Karpathy: the pelican-on-a-bicycle test is finishedx.com/karpathy · 2 Aug

Karpathy gave Opus 5 one paragraph of Tolkien, a 1M-token budget (~$10), and asked for a Three.js render. The model worked ~2 hours and wrote 5,500 lines that procedurally generate the scene. His verdict on the output: "kind of janky but fun." His verdict on what it means: "We're starting to leave the territory where you'd test an LLM by e.g. 'create an svg of pelican on a bicycle'." What he finds striking is the orchestration, since the model has to place polygon assets at (x,y,z) and write the code that animates all of it, with no visual feedback loop. The thread hit the Hacker News front page at 430 points.

Your model-comparison setup is probably still a one-shot prompt scored in seconds, which now discriminates poorly between frontier models. The probe that separates them is a long-horizon task with an explicit token budget, judged on whether the artifact runs. Two practical numbers fall out: a two-hour autonomous run costs about $10 at Opus 5 rates, and 5,500 lines is the working ceiling for a single uninterrupted generation. Budget-capped agent runs are now a pricing unit you can quote a client.

Ship Log

A shared agent lands in Slack channels today, and a single Go binary offers 67 tools over one MCP endpoint.

Claude Tag replaces Claude in Slack todayanthropic.com · 3 Aug

The cutover lands today for Enterprise and Team customers. Claude Tag is multiplayer by design: within a channel there is one Claude, so anyone can see what it is working on and pick up where a colleague stopped. It builds context from the channels it sits in, connects to your tools and data sources, and plans tasks that stretch across multiple days without the original requester staying in the thread. Anthropic says 65% of its product team's code is written by the internal version, including most of Claude Tag itself. Launch credits ($25,000 Enterprise, $2,500 for Team accounts with 10+ paid seats) are Tag-only and expire 1 September.

One agent instance per channel is a different product shape from one agent per user, and it changes what you build. Shared state means the transcript is the audit trail and any teammate can take over a run mid-flight, which removes the "only Dave knows what he asked the bot" failure mode. For a small team, copy the model: scope the agent to a channel rather than a person, let it read the channel as ambient context instead of re-briefing it, and treat handoff as the default. If you run client data through Slack, note that granting channel access grants history access.

Mu: 67 tools, one MCP endpoint, one Go binarygithub.com/micro/mu · 3 Aug

Asim Aslam (Go Micro) posted Mu to Show HN: "the everyday internet as tools" — news, web search, mail, markets, weather, video, places, images, files, calendar, contacts, 67 in total behind one MCP endpoint. The argument is "real tools, not wrappers": Mu runs its own SMTP with DKIM, its own feed aggregators, search indexes, and storage rather than proxying third-party products. Services are Go packages registered in-process, so adding one exposes it across MCP, the CLI, and the web app at once, from the same single binary.

Most MCP servers are a thin shim over someone else's API, which means their reliability, rate limits, and terms are yours to inherit. Owning the service under the tool removes that dependency and makes the tool surface something you can actually version. The in-process registry pattern is the reusable part: define a capability once and get MCP, CLI, and HTTP for free, so you stop maintaining three descriptions of the same tool that drift apart.

Build Patterns

Two answers to the same question — how does an agent prove that what it produced is correct?

Astra ships proofs with machine-checkable certificates attachedgithub.com/openai · 1 Aug

OpenAI ran an internal Astra against ten open problems in mathematics and theoretical computer science, at under $2,000 per problem in token cost, and published the results with a 249-page manuscript plus a 62-page account of how the arguments came together. The headline is the first explicit construction of a non-sofic group, open since Gromov introduced soficity in 1999. Every result ships as a Lean 4 formalization in openai/ten-proofs under Apache-2.0, with a sorry count of zero, so anyone can recompile against mathlib and confirm the proof holds. Simon Willison notes the prompts were not published.

The certificate is what makes the answer publishable, because it lets a stranger verify the result without trusting the model. That pattern generalizes to any domain with a checker: SQL against a golden result set, a schedule against constraint solver output, a tax or contribution calculation against a rules engine. If you can emit a machine-checkable receipt alongside each agent output, review shifts from "does this look right" to running the checker, and the reviewer's expertise stops being the bottleneck. The cost figure is the other signal: under $2k of tokens for a research-grade result resets what an expensive agent run means.

Willison's invisible iframe: let the agent test the app it just wrotesimonwillison.net · 1 Aug

datasette-apps 0.2a0 adds app_debug(), which renders an agent-built app in an iframe set to opacity: 0 and pointer-events: none, then runs JavaScript inside that sandbox so the agent can assert behaviour and measure element dimensions without the user seeing anything. It rides on context.browser_task() from datasette-agent 0.4a0. The release also adds app_list() so the agent can enumerate and edit the apps it has permission to touch.

Generating UI is cheap now; confirming the generated UI actually renders is the gap. A hidden iframe plus scripted assertions is a smoke test that costs one page load and needs no Playwright process, no browser binary, and no screenshot round-trip through the model. Wire it into the generate step so the agent fixes a broken layout before you ever see it, and log what it asserted, since those assertions become your regression suite for free.

Your Radar

Inference economics move on AMD, and a 50% price rise on Sonnet 5 lands at the end of the month.

Kimi K3 runs cheaper per token on MI355X than on a B300wafer.ai · 31 Jul

Wafer benchmarked Kimi K3 (2.8T params) and got 48 tok/s per dollar on an AMD MI355X against 33 on an NVIDIA B300, even though the B300 wins on raw throughput (1,568 vs 952 tok/s). The MI355X is roughly 2.4× cheaper per GPU, and its 288GB of VRAM fits the full weights plus a 1M-token cache on a single node, which a B200 cannot do alone. AMD had day-0 kernel support for K3. The authors conclude "SOTA on AMD is imminent." The post reached the Hacker News front page at 203 points on 2 August.

If you have written off AMD on CUDA-moat grounds, that assumption is now a year out of date and worth re-pricing. The number that matters for agent workloads is tokens per dollar, not peak throughput, since an agent loop burns tokens in bulk and tolerates latency. Fitting a frontier-scale model plus a 1M-token cache on one node also removes the multi-node complexity that usually kills self-hosting for a small team, which matters if client data cannot leave your infrastructure. Check vendor day-0 kernel support before committing, since that is what decided this benchmark.
