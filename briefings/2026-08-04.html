His prediction: human code review survives only as a SOC 2 artifact and is gone within a year.

The cache-hit number is the one to copy: 96% is what makes 69 billion tokens affordable, and it comes from holding prompt prefixes stable across a fleet rather than rebuilding context per agent. Measure your own hit rate before you tune anything else. The Land Rush inversion is worth testing at small scale too. When agents can diagnose in parallel, gating merges serially becomes the bottleneck, and detect-and-repair beats prevent-at-the-gate. Take the account-rotation trick as a warning rather than a recipe, since it depends on subscription terms that can change. And Gas Town is a reminder that a model upgrade is a behavioural change to your orchestration, not a drop-in: pin versions and re-run your agent harness against a new model before it reaches production.

Crawshaw: devtools must be open source, because forks maintain themselves nowblog.exe.dev · 2 Aug

David Crawshaw's argument turns on economics rather than ideology. Customising a tool used to cost more than it returned, because you paid the learning cost up front and the merge cost forever. Both are now near zero. Two prompts do the work: clone the source and modify it locally, then "set up a nightly cron job that executes the prompt: fetch upstream changes to the <software> and rebase all local changes on top of upstream." He added a diff-filtering tool to Shelley, an open-source agent, with a single prompt so commits get pre-processed in the background, something he calls nigh-on impossible against the extension APIs of VS Code or Claude Code. The post hit the Hacker News front page at 513 points on 3 August. Simon Willison added his own version: the friction of reading a dependency has dropped to asking Claude to clone the repo and explain how a subsystem works.

This reframes the build-vs-buy question for every tool in your stack. A closed SaaS tool with a plugin API caps your customisation at whatever the vendor exposed; an open-source equivalent now costs one cron job to keep forked. For a regulated product, the ability to patch a tool's behaviour yourself (redaction rules, audit hooks, data residency) is worth more than the polish you give up. Applied to your own product, the argument cuts the other way: if your customers are advisers who want the workflow bent to their practice, an extension API may be the weaker answer than making the surface agent-editable.

Framer External Agents: point Claude Code at a design canvasframer.com · 3 Aug

Framer now connects Claude Code, Codex, Cursor, and Gemini CLI directly to a project with full access to the canvas, components, and CMS. There is no MCP server to stand up, since an install prompt drops in the bridge the agent talks to. The agent can read and write CMS collections (create, update, delete items), change anything in the project without Framer being open, and publish remotely. Every agent change lands on a branch, so you review before merging to the live version. The point of running the local agent rather than an in-app one is that it keeps your files, scripts, APIs, and command-line tools in reach while it works on the site.

Design tools have been the last place agents couldn't reach, because the state lived in a proprietary document rather than in files. Framer's answer is to expose the document to whatever agent you already run, which is a better pattern than shipping yet another in-app assistant. Two things to take: the branch-by-default rule is the right safety model for any agent that writes to production state, and the install-prompt-instead-of-MCP-config path removes the setup step that kills adoption. If your product holds structured state a client would want an agent to edit (a plan, a model, a document), this is the shape of the integration to build.

Airbnb's eval playbook: 3 layers, 5 judges, 5% of trafficairbnb engineering · Jul

Airbnb's engineering blog sets out eval-driven development as its own discipline, and the specifics are unusually concrete. Evaluation runs in three layers: deterministic programmatic checks first, LLM-as-judge with a written rubric second, human review for edge cases and calibration third. Start from 50-100 hand-labelled examples, including bad ones, before scaling anything. Keep 3-5 well-calibrated judges rather than 20-30 noisy ones, and target high-80s to 90s percent agreement between judge and human. In production, sample 5% of live de-identified traffic daily. For agentic systems, grade individual agent decisions, sub-agent invocations, and tool calls separately rather than only the final answer, using DFS trace reconstruction to walk the reasoning path. One named person decides quality disputes.

The 3-5 figure and the agreement target give you a stopping rule on judge count, which most eval setups lack. The layered order also saves real money, because programmatic checks catch the cheap failures before you spend judge tokens on them. Grading tool calls and sub-agent invocations separately is the part most relevant to a multi-step advisory workflow, where the final document can look right while a lookup silently returned the wrong figure. The named decision-maker earns its place too: without one, rubric disagreements stall releases indefinitely.

Cloudflare: FP8 KV cache doubles usable context, INT4 shrinks GLM 40%blog.cloudflare.com · 3 Aug

Cloudflare published the numbers from quantising its hosted open models on SGLang. Moving the KV cache from BF16 to FP8 took Kimi K2.6's context capacity from about 686,000 tokens to about 1.37 million, raised peak throughput 41% (2,192 vs 1,558 tok/s), and cut cost per token roughly 30%, with negligible accuracy loss across the benchmarks tested. INT4 weight compression took a GLM 5.2 checkpoint from 705GB to 421GB, about 40%, dropping per-GPU memory from 88GB to 52GB and lifting decode speed 55% at single concurrency, 16-27% at higher concurrency, with accuracy within 0.8 percentage points. KV cache integrity checking costs under 1% of throughput and latency.

These are the two levers if you self-host, and the FP8 KV cache one is nearly free: same weights, same accuracy, double the context you can actually serve and 30% off the bill. The context result is the interesting one for agent workloads, since long-horizon runs die on cache capacity rather than parameter count. If you evaluated self-hosting six months ago and concluded the memory maths didn't work, the INT4 numbers move a 705GB checkpoint onto materially cheaper hardware. Both are SGLang features you can turn on rather than research you have to reproduce.

54 of 55 SQLite advisories were LLM fabricationsresearch.jfrog.com · 30 Jul

JFrog investigated a batch of SQLite CVEs and found that of 55 advisories from a single account, 54 were entirely fabricated. The tells: cited code that doesn't exist in the referenced versions, proof-of-concept payloads that trigger no crash, line numbers past the end of the file (line 3555 in a 2,706-line file), and nothing on SQLite's own advisory page. Detector testing pointed to generated text. It got through because NIST cut back manual validation in February 2024, so a plausible advisory sails into the pipeline. The post hit the Hacker News front page at 699 points on 3 August.

Your dependency scanner is downstream of this. Two costs land on you: engineering time burned chasing vulnerabilities in code that was never written, and worse, an automated remediation agent patching against a phantom advisory. If you run agentic dependency updates, add a verification gate before any CVE triggers work — check the advisory appears on the upstream project's own security page and that the cited line actually exists. For a regulated product, this also breaks the assumption behind your vulnerability-management evidence, since "we act on all reported CVEs" is no longer a defensible policy when most reports in a batch can be invented.
