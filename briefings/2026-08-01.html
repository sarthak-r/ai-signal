Willison reframes how much power you hand an agent as a security decision, not an ergonomic one.

Willison's case for stateless MCP: scoped tools over shell accesssimonwillison.net · 31 Jul

Simon Willison shipped three MCP tools this week and argued that MCP is a safer way to build with agents than a terminal. Stateless MCP — one HTTP request, no server-side session — strips most of the implementation complexity of the old two-request protocol, so a server runs like an ordinary scalable web app. His sharper point is about control: scoped tools are "much easier to reason about" and audit than arbitrary command execution, and they stay simple enough that laptop-sized models can drive them. The three tools: mcp-explorer (a uvx-run CLI to probe any MCP server), datasette-mcp (exposes list_databases, get_database_schema, and execute_sql over MCP), and llm-mcp-client (alpha, wires MCP into his llm tool).

The choice between handing an agent a shell and handing it a named set of tools is where you set the blast radius. A scoped tool surface bounds what can go wrong and stays legible to a human reviewer, and it lowers the model bar — a cheaper local model can safely run a tool it could never be trusted with a terminal for. His three tools are a working template for exposing your own data as auditable MCP tools instead of a raw exec endpoint: publish read-only SQL and schema access, not a database shell.

The July release (VS Code 1.127–1.131) lets one agent session hold several related chats, each with its own history, title, and model, and lets you fork a discussion into a peer chat, keyboard-first, with no linear-thread lock-in. Bring-your-own-key models now run inside the Agents window, Copilot vision (images and PDFs in chat) reached GA, dictation landed across chat, editor, and terminal, and agent skills plus MCP went generally available on 29 July.

Branchable chats bring the cheap-experiment habit of version control to agent conversations: try a risky direction in a peer chat without corrupting the main thread, and keep two models working the same task side by side. BYOK-in-agents plus MCP GA means you can route your own model and your own tools through the Copilot agent loop now, so the IDE stops deciding your model and data choices for you.

Build Patterns

Agent memory grows governance — provenance, data labels, and an audit trail baked into the layer itself.

Statewave: agent memory as a governed, provenance-tagged artifactgithub.com/smaramwbc · 31 Jul

Statewave (Apache-2.0, self-hosted on Postgres + pgvector, Python and TypeScript SDKs) launched a memory runtime that stores reproducible, provenance-tagged context bundles rather than doing query-time retrieval. Every memory traces to its source and carries a sensitivity label (pii, financial, secret); declarative YAML policies deny or redact by tag with log_only and enforce modes; and writes leave tamper-evident audit receipts. It's pitched as a self-hosted alternative to hosted memory like Mem0 and Zep.

Two patterns transfer even if you never adopt the tool. Treat retrieved context as a versioned bundle with provenance, so you can reproduce exactly what the agent saw on any given turn instead of re-running an opaque vector search. And push governance down into the memory layer: label PII and financial data at write time and let policy enforce redaction. For a builder running agents over regulated client data, that is the audit trail and data boundary a licensee will ask about, built in rather than bolted on afterward.

DeepSeek moved V4-Flash-0731 to public beta: same 304B architecture as the preview, re-post-trained, now scoring 82.7 on Terminal-Bench 2.1 (agentic coding) against 72.1 for its larger V4-Pro-Preview and 61.8 for the earlier Flash preview. An open-weights model that clears 80 on agentic coding resets both your per-call budget and where the calls can run. Agent loops too costly to run on every request — or that you would rather not send to a hosted API for client-data reasons — become viable on your own hardware at near-frontier quality.
